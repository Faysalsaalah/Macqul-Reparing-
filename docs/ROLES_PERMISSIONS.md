# Roles & Permissions

The shared workspace uses Clerk for sign-in, `app_users` for active shop membership, and normalized Supabase authorization tables. Apply migrations in filename order. Migrations 202610180003 and 202610180004 were applied to the development Supabase project on 2026-10-18.

Tables: `roles`, `permissions`, `user_roles`, `role_permissions`, `user_permissions`, and `audit_logs`. Existing business actions remain in `activity_logs`; access configuration changes are recorded in both activity and append-only security audit history. A user has one selected shop role and optional Allow/Deny overrides. Overrides win over role defaults. Enable and View are required before Create/Edit. Dashboard, Reports and Activity are read-only; Settings supports Edit rather than Create. Payment Edit permits linked refunds; original transactions remain immutable.

Open **Settings → Users & Management → Roles & Permissions**, or **Users and Activity → Roles & Permissions**. Only active Admin accounts can edit access policy. Admin is protected and cannot be restricted through the matrix. New roles start empty. Staff with Users Create/Edit can manage ordinary Staff records but cannot promote Admins, alter Admin records, edit themselves, or change access policy.

The initial Technician role retains the existing technical dashboard, assigned/all repair scope, and diagnosis/status-only behavior. Existing memberships retain their configured repair scope; the initial Technician role has no financial access. Saving that role's matrix switches its members to the module workspace; the UI states this before saving. An explicit Allow override outside the initial technical permissions similarly switches that user to the module workspace. Use a new role for a different staff workflow. Staff can return to `/` using Open Workspace after access changes.

Module menus and direct hash navigation are gated. Server reads project the authorized workspace; hidden financial histories, expenses, activity and unrelated records are excluded. Canonical server mutations overlay only visible changes onto authoritative records, check Create/Edit and repair scope, reject edits to synthetic balance summaries and hidden records, and revalidate business invariants. The database rechecks active membership and effective permissions while holding the shop write lock. Access changes increment the workspace revision, invalidating stale pending writes. Workspace and access reads use one database RPC and a shared shop lock to avoid mixing different access revisions. Direct anon/authenticated table access remains revoked.

Read dependencies are deliberate: Repairs includes device prices, relevant customer/assignee lookups, cost and balance summaries; Customers includes related repair history within repair scope. Parts and Vendors include purchase/balance information needed for their ledgers. Dashboard and Reports include workshop financial data and all repairs. These dependencies are explained above the matrix. A module checkbox controls that module's page and actions; it is not field-level redaction of values also needed by an authorized related module. Creating a repair with a new customer or deposit also requires Customers Create / Payments Create respectively. Stock assignment needs Parts Edit. Payment history requires Payments View. Operational shop configuration is sent for forms and receipts; server secrets are never included.

Tests use isolated PostgreSQL via PGlite. No hosted business records or Staff grants were changed for testing. Real multi-device repair mutation sync and production secret rotation remain separate deployment checks.
